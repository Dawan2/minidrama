# 14. 测试策略(Test Plan):上架级测试金字塔

> **状态**:Wave 1 规范定稿(W1D)
> **适用范围**:minidrama 客户端(App / H5 / 小程序)、后端服务、管理后台
> **配套文档**:[14-quality-gates.md](./14-quality-gates.md)(何时强制执行)、[14-security.md](./14-security.md)(安全测试规则来源)
>
> **总原则**:测试的目的是**验证行为**,不是制造绿灯。禁止空测/假测、禁止删测试换绿、禁止跳过失败(铁律 R2/R3/R5);**CI 必须失败即失败**(铁律 R1)。任何测试在被写下时都应回答:"它失败时说明什么坏了?"回答不了就不要写。

## 1. 测试金字塔(上架级)

```
            ▲  少而准
           /E2E\           ~5–10%   全链路真实环境,只保关键路径
          /─────\
         / 契约  \          横切层   接口/事件兼容性,消费者驱动
        /─────────\
       /  集成测试  \        ~20%    服务+真实依赖(DB/缓存/MQ/沙箱网关)
      /─────────────\
     /    单元测试     \     ~70%    纯逻辑,毫秒级,全量跑
    ▼───────────────────▼  多而快
    (辅助:静态检查/类型系统 —— 金字塔地基,见质量门禁 L1)
```

比例为**用例数量与执行时间分布的指导值**,不是硬性 KPI;真正的硬性要求是各层职责不越界:

- **能用单元测试验证的,不写成集成测试;能用集成测试验证的,不写成 E2E。** 层级越高越慢、越脆,数量必须越少。
- 每层的失败必须能明确定位问题域;E2E 失败排查困难,所以 E2E 只覆盖"用户可感知的关键旅程"。

### 1.1 单元测试(~70%)

- **范围**:纯业务逻辑 —— 订单状态机、金币计价与流水、解锁规则、播放进度合并、审核状态迁移、净化函数、工具函数、客户端 ViewModel/Store 逻辑。
- **要求**:
  - 无网络、无磁盘、无真实时钟(时间注入),单用例 < 100ms;
  - 外部依赖以接口注入 + 测试替身(stub/fake 优先于 mock 断言内部调用,减少脆性);
  - 同时覆盖 happy path 与边界/异常(空值、超限、并发冲突、非法状态迁移);
  - 核心模块(支付/订单、认证/会话、解锁/权益、内容审核)行覆盖率 ≥ 90%,并接受每周变异测试抽检(门禁 §4.7)。
- **执行**:每次 push 全量跑(门禁 G1.4),按模块分片并行。

### 1.2 集成测试(~20%)

- **范围**:服务与真实依赖的协作 —— 仓储层对真实数据库(容器化拉起,禁止用内存库冒充生产库方言)、缓存一致性、消息生产/消费、支付网关适配层对沙箱/本地模拟器、鉴权中间件、数据库迁移脚本。
- **要求**:
  - 依赖用 docker compose / testcontainers 拉起,版本与生产声明一致;
  - 每个用例数据自带自建自清(隔离,可并行);
  - 必测越权样本:用户 A 的 token 访问用户 B 的订单/记录必须 403/404(安全规范 §3.3);
  - 支付回调的验签失败、金额不符、重复通知、乱序通知为必测项(安全规范 §4.2)。
- **执行**:合并级(门禁 G2.2)。

### 1.3 E2E(~5–10%)

- **范围**:见 §5 关键路径清单。真实构建产物 + 真实(预发)后端 + 沙箱支付。
- **要求**:
  - 用例按 P0/P1 分级;P0 = 冒烟集(合并级 G2.3),P0+P1 = 上架全量(发布级 G3.1);
  - 定位符使用稳定的测试 ID(accessibility id / testID),禁止依赖文案与坐标;
  - 每个用例断言**业务结果**(服务端状态、界面可见结果),不只断言"页面没崩";
  - flaky 处置遵循门禁 §7.2:24 小时内修复或带 issue 隔离,禁止无限重试掩盖。
- **工具建议**(以架构槽最终技术选型为准,此处给默认项):App 用 Maestro 或 Appium;H5 用 Playwright;云真机平台跑兼容性矩阵。

### 1.4 静态层(地基)

类型检查(strict)、lint、格式化、SAST、secrets 扫描 —— 全部定义在质量门禁 L1/L2,本文不重复;强调一点:**类型系统是最便宜的测试**,公共 API 与数据模型禁止 `any`/未类型化透传。

## 3. 测试编写规范

- 命名:`被测行为_条件_预期`(如 `unlockEpisode_insufficientCoins_returnsPaymentRequired`),读失败报告即知坏了什么;
- 一个用例一个行为断言主题;禁止巨型"上帝用例";
- 测试数据用构造器/工厂(builder)集中管理,禁止在用例间共享可变全局状态;
- **禁止**:无断言用例、恒真断言、`sleep` 硬等待(用显式等待条件)、断言仅日志输出、捕获异常后吞掉不断言;
- 测试代码与生产代码同等评审标准。

## 4. 契约测试(Contract Testing)

多端(App / H5 / 小程序 / 管理后台)共用后端,接口破坏性变更是集成事故的主要来源;契约测试在不拉起全链路的前提下拦截它。

### 4.1 模式

采用**消费者驱动契约(CDC)**,配合 schema 兼容性检查双保险:

1. **API 契约**:
   - 后端 API 以 OpenAPI 规范为唯一事实源(由 API 设计槽维护),规范文件入库、评审;
   - CI 对每次 OpenAPI 变更做**向后兼容 diff**(oasdiff 等价工具):删除字段、字段改类型、新增必填请求字段、收窄枚举 = 破坏性变更,直接失败(门禁 G1.6);
   - 各消费者(App/H5/小程序)维护自己的契约用例(Pact 或等价:录制"我用到的请求/响应形状"),后端 CI 上跑 **provider 验证**:后端任何改动若破坏任一消费者已发布契约 → 失败即失败;
   - 破坏性变更的唯一合法路径:**先加后删** —— 新增 v2 字段/接口 → 消费者全部迁移(契约更新)→ 按弃用窗口(≥ 2 个发布周期)删除旧字段。
2. **事件契约**(如引入消息队列:支付成功事件、审核结果事件):
   - 事件 schema(JSON Schema / protobuf)入库版本化,兼容性检查同上(只允许加可选字段);
   - 消费者对样例事件做反序列化 + 处理断言。
3. **第三方契约**(支付平台、内容审核服务商):
   - 我方无法要求对方跑契约,改为**适配层 + 录制回放**:以官方沙箱真实响应为夹具(fixture)测试适配层,夹具带来源与日期,定期(每月)对沙箱重放校验夹具未过期。

### 4.2 执行位置

- 消费者契约生成:各端 L1 流水线;
- provider 验证 + 兼容性 diff:后端 L1(门禁 G1.6);
- 契约仓库(broker)记录"哪个消费者版本依赖哪个契约",发布前校验待发布后端版本兼容**线上仍存活的全部客户端版本**(客户端无法强制升级,必须兼容历史版本窗口:约定支持最近 N 个版本,N 由产品槽定,建议 ≥ 6 个月内版本)。

## 5. E2E 关键路径(上架必测清单)

> P0 = 冒烟集,合并级即跑;P0+P1 = 上架全量。每条路径都断言**服务端最终状态**与**界面结果**双侧。

### 5.1 账号与登录

| # | 路径 | 级别 | 关键断言 |
|---|------|------|----------|
| E-01 | 新用户手机号注册 → 登录成功 → 首页加载 | P0 | 会话建立;隐私弹窗在任何请求前出现(安全 §6.2) |
| E-02 | 第三方登录(微信/Apple)→ 首次授权 → 进入首页 | P1 | 服务端换 code 建号;重复登录不重复建号 |
| E-03 | token 过期 → 静默刷新 → 业务无感继续 | P0 | 旧 refresh token 作废(轮换生效) |
| E-04 | 退出登录 / 改密后旧会话失效 | P1 | 旧 token 请求 401 |

### 5.2 浏览与播放(产品生命线)

| # | 路径 | 级别 | 关键断言 |
|---|------|------|----------|
| E-10 | 首页 feed 加载 → 点击剧集 → 免费集起播 | P0 | 首帧时间入性能采集;播放器无错误事件 |
| E-11 | 竖屏沉浸流上下滑切换剧集/剧集内自动连播下一集 | P0 | 切换流畅,进度上报正确 |
| E-12 | 播放中退出 → 再进入 → 断点续播 | P0 | 续播位置误差 ≤ 3s;跨设备登录续播一致 |
| E-13 | 搜索剧名 → 结果页 → 进入播放 | P1 | 未过审内容不出现在结果中(内容安全 §7.1) |
| E-14 | 倍速、清晰度切换、静音/音量 | P1 | 切换后播放连续 |
| E-15 | 弱网(限速 3G profile)起播与播放 | P1 | 自动降清晰度,不崩溃;断网出提示,恢复网后可续 |
| E-16 | 收藏/追剧 → 列表可见 → 取消 | P1 | 服务端状态一致 |

### 5.3 付费与权益(资金安全,全部走沙箱)

| # | 路径 | 级别 | 关键断言 |
|---|------|------|----------|
| E-20 | 播放到付费集 → 拦截解锁页 → 金币余额充足 → 解锁 → 续播 | P0 | 服务端权益记录生成;金币流水正确;重复点解锁不重复扣费(幂等) |
| E-21 | 金币不足 → 充值(IAP 沙箱)→ 到账 → 解锁 | P0 | 服务端收据校验通过才加币;金额与商品一致 |
| E-22 | H5/安卓侧微信/支付宝沙箱支付全流程 | P0 | 回调验签、加币、订单状态 `delivered` |
| E-23 | 开通会员订阅(沙箱)→ 全剧免解锁生效 | P1 | 权益即时生效;到期(沙箱加速)后恢复拦截 |
| E-24 | 支付中断:拉起收银台后取消/杀进程 → 订单不发货,可重新支付 | P0 | 无假发货;订单状态 `closed` 或可续付 |
| E-25 | 退款(沙箱)→ 权益回收 | P1 | 已解锁权益/会员按规则回收 |
| E-26 | 篡改攻击样本:重放旧支付凭证 / 伪造回调(无效签名) | P1 | 服务端拒绝,不发货,产生风控告警(安全 §4) |
| E-27 | 未登录/他人身份访问订单与解锁接口 | P1 | 401/403,越权防护生效 |

### 5.4 UGC 与内容安全

| # | 路径 | 级别 | 关键断言 |
|---|------|------|----------|
| E-30 | 发表评论 → 机审通过 → 可见;命中敏感词 → 不对外可见 | P1 | 服务端过滤,他人账号看不到未过审内容 |
| E-31 | 评论/昵称提交 XSS payload → 渲染为纯文本不执行 | P1 | 安全 §2.2 回归集 |
| E-32 | 举报内容 → 举报单生成 | P1 | 后台可见工单 |
| E-33 | 管理后台下架剧集 → 全端不可见、播放凭证失效 | P1 | ≤ 5 分钟生效(安全 §7.3) |

### 5.5 稳定性与升级

| # | 路径 | 级别 | 关键断言 |
|---|------|------|----------|
| E-40 | 上一发布版本数据升级安装新版本 → 会话/本地数据完好 | P0 | 不掉登录、观看历史保留 |
| E-41 | 长时播放(nightly,连续 2 小时连播) | P1 | 无内存泄漏趋势、无崩溃 |
| E-42 | 前后台切换、来电/中断后恢复播放 | P1 | 播放状态正确恢复 |

## 6. 专项测试

### 6.1 性能测试

- 客户端:冷启动、首帧起播、滑动帧率、内存 —— 每次发布对比基线,回退超预算即门禁失败(G3.3,预算见门禁 §5.4);
- 服务端:核心接口(登录、feed、取播放地址、下单、回调)压测,场景含"热剧上线"峰值模型;SLO:可用性 99.9%,核心接口 P95 ≤ 300ms;
- 压测脚本入库,每次大版本前重跑。

### 6.2 兼容性矩阵(上架级,TikTok WebView)

宿主是 TikTok App 内的 WebView,不是微信小程序,也不是独立 Safari/Chrome 作为上架矩阵(`X-04` / `QA-011`, 2026-08-27)。

- **TikTok iOS**:当前大版本 + 前两个大版本;WKWebView;机型覆盖刘海/灵动岛/小屏,含一台低端机(iPhone SE2);
- **TikTok Android**:Chromium WebView;市场占有率前列的 OEM(华为/荣耀/小米/OPPO/vivo/三星)各至少 1 台,系统覆盖最近 4 个大版本,含 1 台低端机(4GB RAM 中端基线);
- **最低支持 SDK**:与 Portal 配置一致。Safari / Chrome / 微信 WebView 不是本产品的上架宿主,不进入本矩阵。
- 矩阵项跑 P0 冒烟;矩阵清单随市场数据每半年修订(修订=收紧或平移,放宽走豁免)。

### 6.3 安全测试

规则来源见 [14-security.md](./14-security.md):SAST/DAST/依赖扫描在门禁中自动化;E2E 安全样本(E-26/E-27/E-31)随发布全量跑;渗透测试按安全规范 §9 执行。

## 7. 测试环境

| 环境 | 用途 | 数据 |
|------|------|------|
| CI 临时环境 | 单元/集成/契约,容器化即起即销 | 全合成数据 |
| 预发(staging) | E2E、性能基线,配置与生产同构 | 合成数据 + 沙箱支付 |
| 生产 | 灰度验证、监控型合成拨测(每 5 分钟跑登录+起播探针) | 真实数据,只读探针账号 |

- 预发与生产的配置 diff 自动比对,漂移告警;
- **禁止**在生产直接跑写操作类测试(拨测使用隔离的探针账号与免结算商品)。

## 8. 测试数据管理

- 统一测试数据工厂:用户(新客/老客/会员/封禁)、剧集(免费/付费/未过审)、订单各状态 —— 代码化生成,禁止手工库数据依赖;
- **禁止用未脱敏生产数据**(安全 §6.4);需要仿真分布时用脱敏+抽样管道生成;
- 沙箱支付账号、测试手机号池集中管理,密钥走密管(不入库)。

## 9. 缺陷管理与逃逸回溯

- 缺陷分级:P0(资损/崩溃/安全/合规,立即修)→ P3;修复必须附**回归测试**,证明"该缺陷若再现,测试会红";
- 每个线上逃逸缺陷做门禁回溯:本应被哪层拦截 → 在那一层补测试/规则,结论进质量周报(与门禁 §7.3 闭环);
- 上架版本准出:无未修复 P0/P1;P2 需发布负责人书面接受。

## 10. 再次强调(与质量门禁共同生效)

1. **CI 失败即失败**:本计划中所有进入门禁的测试,失败就是流水线失败,禁止合并、禁止发布、禁止上架;不设"警告级测试"。
2. **绿灯必须真实**:禁止删除测试、禁止跳过失败用例、禁止降低阈值、禁止无断言空测换绿(铁律 R2–R5)。测试数量与覆盖率是结果,不是目标;**为绿而空测比没有测试更有害**,因为它制造虚假安全感。
3. 测试策略随架构与产品文档演进:其他槽的接口/技术选型定稿后,本文 §1.3 工具项、§4 契约工具、§6.2 矩阵按实际回填,变更走文档评审。
