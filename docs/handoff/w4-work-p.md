# Handoff — Wave 4, Work Slot P: which hosts a cover image may come from

> **Branch:** `cursor/w4-work-p-53de`, cut from `cursor/w3-work-n-bea1` (`159840f`).
> **Scope:** a fail-closed trusted-host allowlist for cover and poster URLs. The mechanism is a
> pure function in `@minidrama/shared`; the list is a registry in `@minidrama/config`, held level
> with the trusted domains it has to agree with. `image` becomes a trusted-domain usage, so the
> host covers load from is registered where the platform looks for it.
> **Not in scope:** the app UI (history and search are in flight in other slots; `app/src` is
> untouched and the built bundle still hashes `index-B_KnFxaH.js`), the CORS hook and everything
> else under `server/`, which is byte-identical. No pull request was opened.

---

## 1. The problem this slot had to solve

The catalogue fixtures carry cover URLs on `cdn.example.invalid`, and nothing in this repository
had an opinion about that host. Not an approving opinion and not a refusing one — there was no list
to be on. Two different failures live in that gap.

The first is that a cover URL is **content data that becomes a request**. Every other host the
client talks to is one this repository wrote down, against a path this repository wrote. A cover
URL arrives from a licensor delivery, a CMS field or a fixture table
(`docs/12-domain-model.md` §2: `coverUrl`, `horizontalCoverUrl`, the per-episode `coverUrl`), and
it ends up in an `<img src>` unexamined. None of those three sources is a place to take a security
decision, so the decision has to be taken between them and the page.

The second is quieter and it is the one that would have shipped. An image is fetched over the
network, so the platform checks its host against the trusted-domain list like any other request
(`docs/architecture/system-overview.md` §3.2). A cover host that is not registered there renders
perfectly in every environment we can test and is a broken image **on device only** — the exact
failure `packages/config/src/domains.ts` was written to prevent, arriving through a door that file
did not know about, because nothing in it mentioned images.

The obvious fixes are the reason this slot is written carefully:

- **trust the existing trusted-domain list.** It holds the API host. A CMS row could then set a
  drama's cover to `https://api.example.invalid/v1/...`, and the app would fetch it.
- **check the string, not the URL.** `raw.startsWith('javascript:')` is defeated by a leading
  newline, because the URL parser strips control characters before it reads the scheme.
- **ban the dangerous schemes.** A list naming `javascript:` and `data:` still admits `blob:`,
  `about:`, `file:` and whatever the next WebView adds.
- **support subdomains.** A suffix match on `cdn.example.invalid` allows
  `evilcdn.example.invalid`, which anybody can register.
- **make the list configurable so a deployment can fix it.** The list has to match what the Portal
  was told; a deployment that can widen it locally has only made covers load in the one place the
  platform is not enforcing.

### 2.1 The decision, in order

```
   host list has a usable entry? ── no ──▶ refused, NO_TRUSTED_HOSTS
          │                                (an empty or all-junk list trusts nothing)
         yes
          │
   a non-empty string?  ── no ──▶ MISSING / NOT_A_STRING
          │
   parses as an absolute URL? ── no ──▶ NOT_AN_ABSOLUTE_URL   ("/covers/a.jpg", "//cdn/a.jpg")
          │
   scheme is https: ? ── no ──▶ SCHEME_NOT_ALLOWED   (javascript:, data:, blob:, about:, file:, http:)
          │
   no credentials? ── no ──▶ CREDENTIALS_PRESENT     ("https://evil.example@cdn.example.invalid/…")
          │
   no port? ── no ──▶ PORT_NOT_ALLOWED               (":443" is normalised away, so this is a chosen port)
          │
   hostname exactly on the list? ── no ──▶ HOST_NOT_TRUSTED
          │
         yes ──▶ accepted, value = the URL **as parsed**
```

The scheme is judged **after** parsing, which is what closes `"\njavascript:alert(1)"`: the parser
strips leading control characters before the scheme is read, so a string-prefix test sees a
harmless-looking string and the browser sees a script URL.

### 2.2 What an allowlist entry may be

A bare hostname, in the form a URL carries it: lower-case, punycode if internationalised. Entries
are parsed rather than pattern-matched, so an entry and the comparison cannot disagree about what a
host is. `validateCoverHostRegistry` refuses the rest instead of repairing it.

| Refused entry | Reason |
|---|---|
| `https://cdn.example.invalid`, `cdn.example.invalid/covers`, `cdn.example.invalid:8443`, `user@cdn.example.invalid` | not a bare hostname |
| `*`, `*.example.invalid` | a wildcard, which is not honoured even for the name it literally spells |
| `CDN.Example.Invalid`, `köln.example.invalid` | must be written as it is compared (`cdn.example.invalid`, `xn--kln-sna.example.invalid`) |
| the same host twice | duplicate |
| a host no `image` trusted domain covers | it would be blocked on device |
| an `image` trusted domain that is not a cover host | a registered domain nothing may use |

`normalizeImageHost` discards a bad entry rather than throwing, and an allowlist left with no
usable entry refuses every URL. That is why the wildcard case is a refusal and not a hole: a list
of nothing but `*.example.invalid` trusts nothing at all.

### 2.3 The comparison is exact, and the tests are about lookalikes

Five hosts are asserted denied against a list holding `cdn.example.invalid`:
`cdn.example.invalid.evil.example` (a prefix match would allow it), `evilcdn.example.invalid` (a
suffix match would), `sub.cdn.example.invalid` (a domain-suffix match would),
`cdn.example.invalid.` (a match that ignored the root label would), and `cdn.exаmple.invalid` with
a Cyrillic **а**, which is the listed host on a screen and `cdn.xn--exmple-4nf.invalid` to the
parser. Each is a real implementation somebody writes when asked to be flexible about hosts.

## 3. Decisions taken in this slot

Numbering continues from `docs/handoff/w3-work-n.md` §3.

| # | Decision | Reasoning | Cost to reverse |
|---|---|---|---|
| S71 | **Covers get their own allowlist, shorter than the trusted domains** | The trusted-domain registry answers "may the client talk to this host", which is a statement about requests this repository writes. A cover URL is not written here, so reusing that list would let a licensor delivery or a CMS row point the WebView at the API host — a host that is on the list for a completely different reason | One list; two tests |
| S72 | **Schemes are allowed, not banned: only `https:` passes** | A denylist has to enumerate hostile schemes, and it is wrong the first time a WebView adds one. Asserted with `blob:`, `about:` and `file:`, none of which a `javascript:`-and-`data:` denylist would have caught | One condition; five tests |
| S73 | **The scheme is judged after parsing, never from the raw string** | The URL parser strips leading C0 controls and spaces before reading the scheme, so `"\u0000javascript:…"` is a script URL that no string-prefix test sees. One test fails when this is reversed, which is the honest size of it — and it would be zero if the property had not been written down | One line; one test |
| S74 | **The host is compared exactly against the parser's `hostname`** | Prefix, suffix and domain-suffix matches each admit a name an attacker registers, and a homoglyph admits one a human approves. Comparing the parsed form is also what makes the internationalised case decidable at all | One comparison; six tests |
| S75 | **The host list is code, not configuration** | Unlike `CORS_ALLOWED_ORIGINS` (S63), this list must agree with what the Developer Portal was told. A deployment that could widen it locally would only make covers load in the one environment where the platform is not the thing enforcing the rule, so there is no variable to set and nothing to set to `*` | The registry becomes a parser |
| S76 | **An empty or unusable list refuses everything** | The two candidate defaults are "trust nothing" and "trust anything", and only one of them is wrong quietly. There is no host list value that means "any host", including the one somebody reaches for when covers stop loading | One condition; four tests |
| S77 | **The accepted value is the URL as parsed, and the caller renders that** | A validator that approves one spelling while the page uses another is the shape of every sanitiser bypass. Returning the parsed href makes "checked" and "rendered" the same string by construction | One `return`; three tests |
| S78 | **Credentials are refused even when the host is listed** | `https://evil.example@cdn.example.invalid/c.jpg` is a request to the trusted host that reads as a request to another one. There is no legitimate cover URL with userinfo in it, so the ambiguity is simply removed | One condition; one test |
| S79 | **A port is refused, including on a listed host** | `:443` is normalised away by the parser, so this only ever rejects a port somebody chose. Whether a Portal trusted-domain entry carries a port is unconfirmed (U-11), and refusing is the direction that cannot be wrong on device | One condition; one test |
| S80 | **`image` becomes a trusted-domain usage, and the two lists are held level in both directions** | An `<img src>` is a request the platform checks. A cover host absent from the Portal list is a broken image on device only; a registered image domain absent from the cover registry is a slot from a budget of twenty spent on a host nothing may use. Both directions are violations, so the lists cannot drift apart in either | One filter and one loop; five tests |
| S81 | **A wildcard entry is discarded, not interpreted** | `*` is not a forbidden host code point, so `*.example.invalid` survives URL parsing as a hostname. An allowlist holding it would match a URL whose host is literally that and nothing else — a wildcard that looks like it works. Discarding is the only reading that is not a surprise, and it fails closed | One regex; five tests |
| S82 | **An absent cover is a refusal with a name, not an acceptance** | `coverUrl` is optional on an episode. Whether a missing cover means "use the drama's" or "show a placeholder" is the caller's decision, and it is a different decision from "this string is safe to load". `MISSING` says which of the two happened rather than collapsing them | One branch; one test |
| S83 | **`@minidrama/config` depends on `@minidrama/shared`, so the check is one bound call** | The alternatives were duplicating the mechanism in both packages or making every caller pass the host list. A caller who has to supply the list is a caller who can supply the wrong one; `checkCoverUrl(raw)` has no such parameter to get wrong. `shared` is the leaf package, so the dependency introduces no cycle | One import |
| S84 | **The fixture host and the placeholder host are the same host, on purpose** | Fixture cover URLs are now checked by exactly the rule production data is checked by, rather than being exempted by a test-only allowlist that nothing else exercises. `.invalid` is reserved by RFC 2606 and can never resolve, so the placeholder cannot become a real request the way a convenience entry would | One entry |

| The reverse direction unchecked (an image domain need not be a cover host) | **1** | `refuses an image domain that is not a cover host` |

Three rows deserve a note.

The **raw string** defect fails one test, and that single test is the whole difference between a
check and the appearance of one. Every legitimate cover URL still passes, every obviously hostile
one still fails, and `"\njavascript:alert(1)"` gets through — reported as `HOST_NOT_TRUSTED`
instead of `SCHEME_NOT_ALLOWED`, which is a refusal for the wrong reason and would have become an
acceptance the moment somebody wrote a fallback keyed on the reason.

The **entries taken as written** defect fails nineteen, which is the price of the allowlist and the
comparison disagreeing about what a host is. That is the right number: when the two disagree, an
attacker chooses which one to satisfy, so almost everything this suite asserts is downstream of
them agreeing.

The **usage filter** defect fails `accepts the registry that ships in this repository`, which is
worth reading. Dropping the filter makes the API and SDK hosts look like image domains that no
cover host covers, so the registry this repository ships stops validating — the cross-check catches
the loosening from the other side, before any URL is examined at all.

## 5. Registered rather than resolved

**The real image host is unknown (U-IMG-1).** Nothing in the documentation we hold names the host
TikTok's media library serves an `open_pic_id` from, and it cannot be guessed — an allowlist entry
is only useful if it is exactly right. `cdn.example.invalid` is a placeholder in the reserved
`.invalid` TLD, exactly as `api.example.invalid` beside it is. When a real cover URL is seen on a
device or in a media-library response, **two entries change together**: `TRUSTED_COVER_HOSTS` and
the `image` entry in `TRUSTED_DOMAINS`. `validateCoverHostRegistry` fails if only one of them is
edited, and `pnpm gen:minis-config` has to be run afterwards.

**The trusted-domain budget now has an image host in it.** Three of twenty are spent
(`docs/architecture/tech-stack.md` §6). If posters and covers turn out to be served from more than
one host — a separate horizontal-cover CDN, a separate poster host — each is another slot, and the
budget is the reason that is a decision rather than a detail.

**`@minidrama/server` does not depend on `@minidrama/config`.** Nothing forced it to before this
slot. Whoever wires the catalogue module has to add `"@minidrama/config": "workspace:*"` to
`server/package.json`; the alternative — importing `checkImageUrl` from `@minidrama/shared` and
passing a host list assembled locally — is the mistake S83 exists to prevent.

**`@minidrama/app` has `@minidrama/config` as a dev dependency only.** The package's root export
is browser-safe (`paths.ts`, the only module that touches `node:fs`/`node:url`, is deliberately not
re-exported from `index.ts`), so promoting it is a one-line change if the client ever needs to
check a cover URL itself. Whether it should is §7.

## 6. Deliberately not built

- **No caller.** Nothing in `server/` or `app/` invokes this yet. There is no catalogue module on
  this branch to invoke it from, and inventing one here would collide with the slot that owns it.
- **No fixture edits.** The catalogue fixtures are not on this branch. They already use
  `cdn.example.invalid`, which is why S84 makes that the registered host: the fixtures pass
  unchanged, and they pass because they satisfy the rule rather than because they are exempt.
- **No image proxy, and no rewriting of a cover URL.** A refused URL is refused. Repairing one —
  upgrading `http:` to `https:`, moving a path onto a trusted host — would mean this module
  guesses what the content team meant, and a guess that is right nine times is a hole the tenth.
- **No `srcset`, size or format policy.** The query string is passed through untouched, because CDN
  resize parameters live there. What a sensible cover size is belongs to the UI slot.
- **No content-type or byte-level check.** Whether the trusted host serves an image is the trusted
  host's business; this decides *which host*, and nothing more.
- **No API-response validation.** The obvious next step is refusing to emit a catalogue item whose
  cover fails this check, but where that happens — at ingest, at read time, or both — is a decision
  for the module that owns the endpoint (§7).
- **No error code.** `ImageUrlRejection` is not an `ApiErrorCode`: no client recovers from a bad
  cover URL, and the fix is a content edit. If a catalogue endpoint ever surfaces one, it is a
  server-side log line, not a code in the envelope.

## 7. For the next slots

**For whoever builds the catalogue module.** Add the `@minidrama/config` dependency and call
`checkCoverUrl(raw)`. Two properties are worth honouring rather than rediscovering: the value it
returns is the URL as parsed and that is the string to store or serve (S77), and a refusal names
its reason so a log line can say *why* a drama has no cover. The interesting design question this
slot deliberately left open is **when** to check — refusing a bad cover at ingest keeps the
database clean but makes a licensor's typo an import failure, while checking at read time keeps the
import forgiving and means every response pays for it. Both are defensible; doing neither is not.

**For whoever owns the feed and detail UI.** Do not build a URL and do not sanitise one. If a
cover reaches the client it has been checked; if the field is empty, that is the `MISSING` case and
it wants a placeholder, not a fallback URL assembled from an id. The one rule that survives into
the client: render the string that came out of the check, never the one that went in.

**For whoever gets a real cover URL from the platform.** §5 — both lists, then
`pnpm gen:minis-config`, then the Portal. If the real host turns out to need a port or a wildcard,
that is a platform fact worth writing down rather than a rule to relax: S79 and S81 are refusals
because nothing we hold says either is needed.

**For whoever adds another kind of image.** Avatars, share cards and app icons are the same
mechanism with a different list. `checkImageUrl` takes the hosts as an argument precisely so a
second list is a second registry rather than a second implementation — and a second registry is
also a second trusted-domain slot, which is the part that has a budget.

## 8. Known gaps in this slot's own work

- **The host that matters is not known (U-IMG-1).** Everything here is proven against a fixture
  host in a TLD that cannot resolve. The first real cover URL decides whether one host is enough,
  and whether it is a host or a path on one we already trust.
- **Nothing is proven in a browser or on a device.** The assertions are about which strings this
  code accepts. Whether the platform's trusted-domain check treats an `<img src>` exactly like a
  `fetch` is read from the documentation, not observed — and it is the premise S80 rests on.
- **A trailing-dot host is refused, and that is a judgement call.** `cdn.example.invalid.` is the
  same name to DNS and a different string to the parser. Refusing it is safe and slightly wrong;
  accepting it would mean normalising a form no CDN emits. If a real feed produces one, this is the
  line to revisit.
- **Nothing checks the list against the Portal.** `validateCoverHostRegistry` holds two lists in
  this repository level with each other. Whether either matches what a human typed into the
  Developer Portal is unverifiable from here, and it is the same standing gap
  `docs/handoff/w1-skeleton.md` records for the trusted domains.
- **A refused cover is a return value and nothing else.** No metric, no log line, no alert — this
  slot has no caller, so there is nowhere to put one. A feed that silently shows placeholders
  because a content migration changed CDN hosts would look like a design choice until somebody
  opened the response.
