## 2. 关键决策与理由

1. **失败即失败写成铁律 R1,且由 CI 技术强制**(禁止 `allow_failure`/`continue-on-error`),人工评审仅为第二道防线;admin 绕过门禁自动留痕通报。R2/R3/R5(删测试、跳过、空测)配了具体的 CI 检测手段(diff 扫描 skip 标记须带 issue+到期日、无断言检测、核心模块每周变异测试),不是口号。
2. **阈值只升不降(ratchet)**:覆盖率等门禁阈值单调收紧,放宽唯一通道是双签+限期(≤14 天)+CI 显式标注的豁免流程;且失败即失败、删测试、跳过、空测四条**无豁免通道**。
3. **门禁分三级**(PR ≤10min / 合并 ≤30min / 上架 ≤2h),用速度分层换取"每次 push 都有硬门禁"而不拖慢开发;上架级额外含兼容矩阵、性能基线、安全/隐私/内容安全清单与灰度放量门禁(崩溃率、支付成功率、播放失败率自动熔断)。
4. **支付为最高风险域**:定价与发货真相只在服务端;IAP 收据、微信/支付宝回调全部服务端验签 + 金额核对 + 幂等 + 每日对账;相关模块覆盖率下限 90%,E2E 含篡改/重放攻击样本(E-26)。
5. **契约测试作为金字塔横切层**:多端共用后端,采用 OpenAPI 兼容性 diff + 消费者驱动契约双保险;破坏性变更唯一路径是"先加后删 + 弃用窗口",并要求兼容线上存活的历史客户端版本。
6. **内容安全按"先审后发"设计**并纳入上架门禁(词库版本确认、一键下架 5 分钟生效且每季度演练)——这是国内短剧平台的合规生命线,不做成事后补丁。
7. **不为绿而空测**:本 Wave 仓库尚无代码,因此**没有提交任何测试代码或 CI 配置文件**,只交付规范;规范中明确规定 echo-only/恒成功的占位 CI 步骤与无断言测试禁止合入。首个代码 PR 必须同时落地 L1 门禁(见 §4 待办)。

## 4. 给后续 Wave 的落地顺序建议

1. **随首个代码 PR 同步落地 L1 门禁**(lint、typecheck、单元测试、diff 覆盖率、secrets 扫描、skip/空测检测)+ 分支保护规则——门禁必须先于代码量增长,事后补门禁成本剧增;
2. 首个服务联调前落地契约门禁(OpenAPI diff + provider 验证);
3. 首次接入支付沙箱时同步编写 E-20~E-27 支付 E2E;
4. 首次提审上架前 4 周开始跑 L3 全量(兼容矩阵与云真机需要提前采购/接入);
5. 变异测试、无障碍门禁可在核心模块稳定后再启用(已在文档中标注为阶段性项)。

## 5. 风险提示

- 文档中的阈值(覆盖率 80%/60%/90%、包体积、起播 P90 等)为**行业合理初始值**,允许在数据积累后收紧;任何放宽必须走豁免流程,不得私改。
- 最大的执行风险不是技术而是纪律:赶工期时"先跳过这个失败测试"的第一次破例会摧毁整套体系。已通过 CI 技术强制 + 绕过留痕 + 周报通报三层手段对冲,请各槽位负责人共同维护。
